# 取件计次语义重构（2026-10-24）

> 状态：已实现（core 工作区）｜破坏性变更｜随下一次发布列车发版
> 触发：2026-10-23 口径收口后的第三轮审计（独立代理 + 自查复核）

## 1. 一句话

**「一次取件」= 一次内容交付 = 一个下载令牌（取件会话）；同一个令牌至多扣 1 次取件次数。**

扣次从「每个下载请求」移到「内容交付前」，并与令牌绑定；「次数耗尽」不再混作「过期」。

## 2. 修的是什么（缺陷清单）

| # | 缺陷 | 症状 | 严重度 |
|---|---|---|---|
| D1 | 匿名取件 retrieve 自己扣次，随它下发的直链下载又扣一次 | 一次取件扣 2 次，count 样式下对方可用次数直接减半 | 高 |
| D2 | 扣次点在**每个下载请求** | 多文件逐个下载逐个扣 ⇒「取件次数=1 的多文件分享只能下载第一个文件」，而打包 zip 只扣 1 次 ⇒ 两条 UI 路径不可比 | 高 |
| D3 | 「次数耗尽」混在 `IsExpired` 里 | **按取件次数的分享，走取件码通道时最后一次取件必然 404 拿不到文件**（retrieve 扣到 0 ⇒ 判过期 ⇒ 下载被拒）；分享页通道却能拿到 ⇒ 两条通道结论相反 | 事故级 |
| D4 | 扣次早于子文件归属校验与 zip 组装 | `file=` 不属于该分享 / zip 组装失败 ⇒ 404/500 但次数已被吃掉（白扔一次取件机会） | 高 |
| D5 | 文本分享在 select 即交付正文，却从不扣次、不记取件人、不写传输日志 | owner 设的「按取件次数」上限对文本分享形同虚设；传输日志对文本分享失明 | 高 |
| D6 | 令牌签发按**规范码**、校验按**请求原始码** | 用户把下载 URL 的 code 换成 6 位取件码 ⇒ 401「令牌无效」（令牌本身是好的） | 中 |
| D7 | 锁定「预检键=原始码 / 记账键=规范码」分叉 | 6 位码入口的 429 预检恒不命中（只有深层闸门拦得住） | 中 |
| D8 | `security.download_token.validity_seconds` 从未被读取 | 运维改配置无效（硬编码 1000s） | 低 |
| D9 | `ErrDownloadToken` 定义了从不使用 | 死代码 | 低 |
| D10 | 匿名取件结果页 `remaining_count` 恒发 0 | 页面显示「剩余可取次数 0」，用户以为文件已失效 | 低 |

附带收口：`pkg/codex` 违反架构守卫规则 1（pkg 不得 import repo）⇒ 解析器下沉到
`repo/db/dao.ResolveByCode`，占位判定 `IsNotReady` 迁到 `model`（此前 core main
的架构棘轮就是红的，会挡住发版列车）。

## 3. 新语义（不变量）

1. **扣次点 = 内容交付前**：
   - 文件分享：`GET /share/download` 交付时扣；
   - 文本分享：`GET /share/select` 交付正文时扣（select 就是交付面）；
   - 匿名取件：`POST /anonymous/retrieve` **只发凭证，不扣次**。
2. **一个下载令牌 = 一次取件会话**：同一令牌下的多次交付（多文件逐个下载、打包
   zip、断点续传 Range、重复点击）**只扣 1 次**，只记 1 个取件人。
3. **次数耗尽 ≠ 过期**：`IsExpired()` 只判时间；`IsCountExhausted()` 独立判定。
   耗尽 ⇒ 拒绝**发起新的取件**（`20004` 超过取件次数 / 匿名通道 `20007`），
   **已扣次的那一次取件仍可完成交付**（D3 的正解）。
4. **失败不消耗次数**：归属校验、zip 组装等前置校验全部在扣次之前完成。
5. **令牌校验按规范码**：下载端点先解析码（6 位取件码 / 8 位分享码都能用），
   再按规范码验签。
6. **锁定键统一用规范码**：预检与失败记账同一把钥匙（6 位码入口与 8 位码入口
   共享爆破预算，预检真正生效）。
7. **两个交付面的判重粒度不同**（2026-10-24 回归修复，v0.32.2）：
   | 交付面 | 判重键 | 理由 |
   |---|---|---|
   | 文件下载 | 下载令牌指纹（一次下载会话 = 一次取件） | 交付动作 =「下载」；同一会话内的多文件逐个下载/断点续传不重复扣 |
   | 文本交付（取件页） | (分享码, 取件人 IP) | 交付动作 =「打开」；同一 IP 重复打开/刷新 = 同一次取件（否则刷新一次扣一次，收件人刷新两次就 403、正文都看不到）；不同的人各扣 1 次 ⇒ owner 的「N 次」= N 个取件者 |

   ⇒ **推论**：文本的「取件次数」= 不同取件者的次数（不是页面加载次数）。
   ⇒ 「次数用完」的预检须先判「本次取件是否已计次」：**已取过的人仍可再打开**。

## 4. 实现要点

| 层 | 落点 |
|---|---|
| 模型 | `model.FileCode.IsExpired()` 只判时间；新增 `IsCountExhausted()` / `IsPickupAvailable()` / `IsNotReady()` / `PickupCodeLength` |
| 计次 | 新表 `pickup_charges`（唯一索引 `(code, token_hash)`）：`dao.ChargePickupOnce` ⇒ 登记（ON CONFLICT DO NOTHING）+ 原子扣减；扣减失败**撤销登记**（否则该令牌被误判成「已计次」而免费放行） |
| 令牌 | `pkg/security`：形态 `exp.nonce.sig`（nonce 保证同秒签发的令牌互不相同 ⇒ 计次键可靠）；计次指纹 = `HMAC(secret,"fp|"+token)`（**单向**，落库的不是令牌本身 ⇒ DB 泄漏不等于泄漏下载凭证）；TTL 接配置 |
| 编排 | `app/share.Service.ChargePickup` → handler `chargePickup`（扣次 + 记取件人同点） |
| 迁移 | `000004_pickup_charge`（版本化）+ `AutoMigrate` 兜底；`janitor.CleanupPickupCharges` 按令牌 TTL 清理 |

## 5. 破坏性变更清单

| 变更 | 影响面 |
|---|---|
| 下载令牌形态 `exp.sig` → `exp.nonce.sig` | 升级瞬间在途令牌失效（窗口 ≤ TTL，取件页重新取一次即可） |
| 匿名取件 retrieve 不再扣次 | 依赖「取件即扣次」的集成需改为在下载后观察 used_count |
| 「次数耗尽」错误码 `10003`（无权限）→ `20004`（超过取件次数）/ `20007` | 前端 i18n 已有 20004/20007 文案，无需改动 |
| `pkg/codex` 下沉（公开包消失） | 仓内 5 个域已同步；外部依赖方（若有）需改用 `repo/db/dao.ResolveByCode` |
| `share.Service.GetFileWithUsage` 去掉 `recordViewer` 布尔位 | 记取件人改由计次点触发 |
| `model.FileCode.IsExpired()` 不再含次数语义 | 依赖「次数=0 ⇒ 过期」的下游判定需改用 `IsCountExhausted()` |

## 5.2 「拆开一个判定 ⇒ 必须逐个门重审」（3.3.23 / core v0.32.4）

**这轮自己踩的坑**：上一轮把 `IsExpired()` 拆成「只判时间」+ `IsCountExhausted()`。
拆分前 `IsExpired()` **含次数语义**（`ExpiredCount==0 ⇒ 过期`）⇒ 凡是以
`IsExpired()` 为闸的门，此前**同时**挡着「次数耗尽」；拆分后这些门只挡时间
⇒ **次数闸在四个面被漏掉**：

| 面 | 漏闸后果 |
|---|---|
| `/share/metadata/:code` | 额度用完后仍回显文件名/大小/统计（旧口径 404） |
| `/anonymous/search/:code` | 同上（旧口径 404；**该面此前没有任何测试** ⇒ 漏闸无人发现） |
| MCP `get_share_content` | 额度用完后仍回传**文本正文** |
| MCP `download_share_file` | 额度用完后仍把**文件内容** base64 回传 |

MCP 两个工具尤其要紧：`share_text`/`share_file` 支持 `count` 样式（按取件次数）
⇒ 这类分享的「最多取 N 次」承诺在 MCP 读回面完全失效。

**反向的坑（本轮第一版就踩了）**：修的时候把次数闸放进 `Peek`（匿名域的公共
查面）里、把耗尽态吞成 `ErrCodeNotFound` ⇒ `/anonymous/download` 与
`/anonymous/search` 先拿到「码不存在」⇒ **handler 里既有的 20007 分支变成死
代码** ⇒ 「次数耗尽」又退回了「不存在/已过期」的伪装（正是这次重构要消灭的
东西）。⇒ 正解：**`Peek` 只判时间过期，耗尽态交由调用方按各自口径判定**。

⇒ **纪律**：
1. **拆开一个判定 = 逐个重审所有以它为闸的门**（不是「改一个函数」，是「改
   一族门的语义」）⇒ 用 `grep` 把判定点全捞出来逐个对照，别凭印象。
2. **拆分后要拿旧口径做基线**：旧实现里「这个门同时挡了什么」是隐含契约，
   拆分时要显式继承（这里 = 「次数耗尽」也算失效）。
3. **公共查面不要替调用方做业务判定**（`Peek` 吞耗尽态 ⇒ 调用方的独立错误码
   永远发不出来）⇒ 判定权归**出口面**，共享层只做「查得到没有」。
4. **没有测试的面 = 漏闸不会被发现**：`/anonymous/search` 此前零测试 ⇒ 补
   闸时才发现它整条链路都缺断言。
5. 补闸必须配**负对照**（改回缺陷态即变红），否则「测试全绿」可能只是因为
   断言写错了地方。

## 5.3 「闸门组合不能靠人记」⇒ 取件闸门契约守卫（3.3.24 / core v0.32.5）

**根因还没被消掉**：v0.32.4 修掉了「四个面漏闸」这个**具体缺陷**，但漏闸的
**根因**是「闸门组合是每个面各自手搓的」⇒ 新加一个面时，没有任何机制要求
作者声明「这个面交不交付内容、次数耗尽时怎么判」⇒ **漏闸是默认结果，不是意外**。

⇒ 把它变成**可机械拦截**的（`bootstrap/share_surface_contract_test.go`）：

| 守卫 | 拦什么 |
|---|---|
| ① 表内每条路由必须真实存在 | 陈旧条目（面删了表没删） |
| ② `/share/`、`/anonymous/`、`/preview/` 前缀下的面必须全部在表内 | **新增面向外的东西忘登记** |
| ③ MCP 侧「读分享内容」的工具必须在表内 | 新增读内容的 MCP 工具忘声明 |
| ④ 表内声明的**覆盖测试函数必须真实存在**（源码树检索） | 空头承诺（测试被删/改名） |
| ⑤ 闸门口径取值必须落在受控词表 | 写「差不多」的口径，机械不可判定 |

配套：MCP 侧把「该工具读不读分享内容」标进**工具注册表本身**
（`toolSpec.Gate{ReadsShare, Exhausted, CoveredBy}`）⇒ 注册表仍是单一真相源。

**契约表同时是一份活的规格**：每个面交付什么 / 次数耗尽时给哪个码 / 由哪个测试覆盖。

**一个必须钉死的语义分岔**：不同面的**闸门点不同**，不是实现随意——
- `/share/download` 的闸门在**内容交付那一刻**（`chargePickup`），**不在授权阶段**：
  挪到授权阶段会把那个**已经付过费**的取件会话（同一下载令牌）挡掉 ⇒
  「已扣次的那一次取件仍可完成交付」这条不变量就破了。
- 其余面在**授权/查询时**就拒（20004 / 20007）。

⇒ 契约表的 `Gate` 列必须能表达这个分岔（词表含「交付点扣次」）。

**负对照（守卫必须能变红，均已实测）**：契约表少一条 ⇒ ② 红；覆盖测试名写错 ⇒
④ 红；**新增一个 `/share/` 路由而不登记 ⇒ ② 红**（防复发的核心）。

## 5.4 「一次上传 = 一个分享」需要**幂等键**（3.3.25 / core v0.32.6）

**缺口（2026-10-24 跨仓审计发现）**：chunk/presign 的 `Complete` **不检查是否已建过
分享** ⇒ 同一 `upload_id` 二次 Complete（双击 / 客户端重试 / 网络重试）会**再建
一条分享**：

- 两个分享各有**独立的取件次数额度**与取件码 ⇒ owner 设的「最多取 N 次」实际可取
  **2N** 次 ⇒ **直接击穿取件计次承诺**（与 §5.2 的「漏闸」是同一族后果的另一层：
  一个是**没拦住**，一个是**多建了一份**）；
- 用户存储统计双计；chunk 每次合并生成新的 UUID 物理路径 ⇒ 磁盘留下第二份。

**真机实测已发生**：13 条带 `upload_id` 的分享里已有 **1 组重复** ⇒ 生产数据已被
污染（重复那条独立铸取件码、独立计次）。

⇒ 修法：**以 `upload_id` 为幂等键**（`dao.FirstByUploadID` + 域级
`FindShareByUploadID`）——完成面先回读，命中即**复用同一个分享码**。
chunk 的回读放在**合并分片之前**（重试不该再合并出第二份物理文件）。

⇒ presign 另有一处顺序缺陷：**标记 complete 在建分享之前** ⇒ 建分享失败（配额/
审核）时 meta 已标记 ⇒ 客户端重试只得 `ErrAlreadyComplete` ⇒ **已上传对象永久
成孤儿** ⇒ 把标记挪到建分享**之后**（失败可重试），并让「已标记」路径走幂等回读。

**通用判据**：**任何「可被重试的写操作」都要有幂等键**。没有幂等键时，
「重试」= 「重复创建」⇒ 重复创建的每份都带独立配额 ⇒ 配额语义整体失真。

## 5.5 发布流水线：跨仓产物在**非 shipped 态**必然落后 ⇒ 不得强校验

**缺陷（2026-10-24，3.3.24 列车 tagged/shipped 两阶段各假红一次）**：
`trainctl verify` 对 **hub Latest** 与 **charts** 的校验在非 shipped 态也强校验，
而这两个跨仓产物**不是与 state 同时到位的**：

- hub 的 `v<train>` Release 是 finalize **推 tag 之后**才由 release.yml 创建的
  （finalize 先提交 `state=shipped` ⇒ 那个 push 就触发了 verify 工作流 ⇒ 校验跑在
  Release 建好之前，实测约 40 秒窗口）；
- charts 的 Chart.yaml 提交被**显式推迟**到 advance（镜像在位后才直提，否则
  chart 发版会指向还不存在的镜像）⇒ tagged 态 charts 必然还是上一车。

⇒ 修法：跨仓产物只在 **shipped 态**强校验（`isShippedPhase`），其余态告警；
shipped 态给**有界重试**（窗口耗尽仍不符 ⇒ 照常判红，**不削弱门禁**）。

**通用判据**：**门禁的判定输入不能是「当前状态」，而要是「该状态下应该已经
到位的产物」**；「还没到位的产物」在非终态必须降级为告警。

### 7.2 owner 侧的逐条取件历史（**已随 3.3.19 落地**，2026-10-24）

**缺口**：`file_codes.viewer_ip/viewer_at/viewer_count` 只有「最后一次 IP + 累计
次数」⇒ owner 在「取件历史」页看不到逐条记录（他只能靠到件通知逐条得知）。

**关键发现：明细数据已经存在，不必新表** —— `transfer_logs` 逐条记录了每次下载
（IP / 时间 / 操作码），且本轮给文本分享补了写入（`logTextView`）。
⇒ 缺的只是「**owner 自己的视图**」（目前只有管理端的传输日志页能看到明细）。

**落地实况（3.3.19 上线；3.3.18 因 frontend-core 版本未抬而作废，见下）**：

1. **contracts v0.18.6**（已发布，tag 在 bump 之前）：`idl/share.thrift` 的
   `UserShareItemData` 加 `26: optional list<PickupRecord> pickups`，
   `PickupRecord { picked_at, ip, channel }`；三条生成链
   （`gen-model.sh` / `cmd/gen-openapi` / `cmd/gen-ts`）全对账一致。
2. **core v0.32.1**：**数据源不是 transfer_logs 而是计次记录表**
   （`pickup_charges`，一次取件 = 一行 ⇒ 多文件逐个下载/断点续传不会被显示成
   「取件 N 次」——transfer_logs 是「每次下载一行」，用它会把一次取件显示成 N 次）。
   计次记录新增 `ip` 列（迁移 000005）；`ListUserShares` 组装 `pickups`
   （最近 20 条，取不到不阻断列表）。
3. **frontend-core**：取件历史页加「取件明细」列（标签显示「N 次取件」，
   hover 出逐条 IP/时间/交付面）；contracts 的 tgz 钉版抬到 v0.18.6；
   通道判定抽成可测纯函数 `utils/pickupChannel.ts`（本仓约定：utils/composables
   才测，view 层无组件测试基建）。
4. **守卫**：`scripts/smoke-full.sh` S21 端到端断言（取件一次后该分享项必须带
   1 条明细且 IP 非空）——本地真机 PASS=70 FAIL=0。

**发版插曲（3.3.18 作废 → 3.3.19 接手）**：3.3.18 的 frontend-core 钉版滞后
（内容已变但**库线版本没抬** ⇒ 它的 tgz 还是旧的 ⇒ 前端镜像里没有明细列），
而 `v3.3.18` tag 不可重切 ⇒ 按守门逃生口人工置 `state=shipped` 放弃 3.3.18，
由 3.3.19 带 `frontend-core=v0.11.17` 重新发车。
⇒ **教训：库线（contracts/core/frontend-core）内容变了就要抬自己的版本**，
否则消费方钉到的 tgz 还是旧的；列车只改 hub 的 pin，不替你抬库线版本。
