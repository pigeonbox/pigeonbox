## 0. 结论

4.9.1 之后，**功能面已经不是瓶颈**。瓶颈是这一句：

> 发出去的版本，到不了已经在运行它的机器上。

四条实测证据（不是推测）：

| # | 事实 | 证据来源 |
|---|---|---|
| 1 | 修「管理员口令重置丢归属 + 硬删泄漏」的 4.8.6 发车前，某台 fnOS 真机已停在 **4.1.2** 约三周 | 2026-11-04 真机实录（升级后逐项对账） |
| 2 | 同一台机器上普通管理员**停不下服务、改不了 manifest**（`kill` 与三处 manifest 副本均不可写）⇒ 手工换包不可行 | 2026-11-06 实测（三道硬墙） |
| 3 | 全生态**没有任何「检查更新」能力** | 远端 core 文件树无 version/upgrade 检查实现；`pb` 子命令 = `put/import/ls/url/rm/storage/doctor/p2p×4`；维护页只有「清理过期 / 优化 / 系统信息」 |
| 4 | 备份只有**离线子命令**（停服 + `--yes`）；后台任务只有「过期清理 1h / janitor 24h」两件（**定时备份已随 5.1.0 补上**） | `core/bootstrap/tasks.go` · `server/cmd/server/backup.go` |

⇒ 后续三趟车按 **「让版本能到达 → 让账号可信任 → 让新人能上手」** 排序。
功能增量（目录上传、多语言）放第三趟，**不抢主线**。

## 2. 主线选择的理由，与被否决的备选

**选「生命周期」为主线**，因为它是唯一一条「做了之后，过去所有工作都增值」的线：
每修一个缺陷、每加一层防护，都会通过升级通道真正抵达用户。反过来，
不解决到达率，继续加功能只是让**升级落差更大**。

被否决的备选（不是不好，是优先级更低）：

| 备选 | 为什么不排在前面 |
|---|---|
| 继续扩存储后端 / 部署面 | 边际收益已很低：14 后端覆盖了绝大多数场景，新平台（如某个 NAS OS）收益小于维护成本 |
| 做「分享访问分析」 | 已有 TransferLogs / Activities / 取件明细，缺的是**运营解读**而非新数据 |
| 做客户端 SDK（TS/Go/Python） | `docs/UPLOAD-PROTOCOL.md` 已经把协议写清；真需求出现前先不预造 |
| 重做前端框架/设计系统 | 无痛点驱动；4.9.0 已做完一轮审计修复（含无障碍） |

## 3. 三趟车

### 3.1 生命周期（零破坏）｜A=5.0.0 · B=5.1.0 已发货，C 仍顺延

> 主题：**这台机器知不知道自己落后了，落后时会不会丢数据。**

#### A. 更新检查（update availability）

- **问题**：运维没有「我落后了」的信号；文档站的新版本公告到不了机器。
- **形态**：
  - core 的 `/admin/diagnostics` 增 `update` 段：`current` / `latest` / `checked_at` /
    `source`（`github` / `disabled` / `unknown`）/ `channel`（`stable`）。
  - 数据来源 GitHub Releases API，**24h 落盘缓存 + ETag**；超时 5s；
    离线 ⇒ `source=unknown`，**不是故障**。
  - 开关：`update.check_enabled`（默认 **开**，env `PB_UPDATE_CHECK_ENABLED=false` 可关）。
  - 端点可用 `update.endpoint` / `PB_UPDATE_ENDPOINT` 指向企业内网镜像（**只允许 https**，localhost 例外；
    不跟随跳转）。
  - `pb doctor` 增一项「新版本可用」：**INFO 级**，不改变退出码（0=健康），
    否则 CI 会因为「上游有新版本」恒红。
  - 管理台维护页显示「当前 vX / 最新 vY / 升级说明」链接。
- **落点**：core（diagnostics + 缓存 + 配置）· server（`pb doctor`）· frontend-core（维护页）
- **破坏性**：无（新增字段，不删不改）
- **规模**：小～中（约 300 行含测试）
- **验收判据**：
  1. 断网（负对照：把端点指到 `127.0.0.1:1`）⇒ `unknown`，doctor 退出码仍 0。
  2. 有新版本 ⇒ 维护页显示，doctor 显示但退出码仍 0。
  3. 请求体不含任何实例标识（无 site id / 无分享码 / 无用户信息）。
  4. 缓存命中时**不发出站请求**（用本地假端点计数证明）。
- **风险**：GitHub 未认证 API 60 次/小时 ⇒ 必须靠缓存与 ETag，不能「每次打开后台都查」。

#### B. 定时自动备份 —— ✅ 5.1.0 已发货

- **问题**：备份包能力早就有了，但要求**停服 + 显式 `--yes`** ⇒ 实际没有人备份；
  而升级失败、误删、磁盘故障都靠它兜底。
- **已实现形态**（配置键名与规划稿不同，以此为准）：
  - core 后台调度器（**只在 admin 副本跑**，`ServesAdminPlane()` 内装配）：
    `backup.enabled`（默认 **关**）· `backup.dir`（默认 `<datapath>/backups`，相对路径**按数据目录**解析）·
    `backup.keep`（默认 7；**`<=0` = 不限**）· `backup.at`（默认 `03:00` 本地时）。
    env：`PB_BACKUP_ENABLED` / `PB_BACKUP_DIR` / `PB_BACKUP_KEEP` / `PB_BACKUP_AT`。
  - **调度语义**：10 分钟轮询 + 「时刻已过 + 当天无包」判定，而不是「睡到明天 03:00」
    ⇒ 对重启、改配置、时钟跳变免疫。幂等**靠目录自证**（文件名带日期），不另存状态文件
    —— 状态文件会与目录分叉（人删了包仍说「今天跑过了」）。
  - **一致性**：直接复用既有备份包格式（`manifest.json` + `db/backup.db` 一致快照 +
    `files.json` 清单 + `objects/` + 逐对象 sha256）⇒ 与离线子命令产物**同格式**，可互相恢复。
  - **写入原子性**：先写 `<name>.tar.gz.partial` → `Sync` → `Rename` ⇒ 半截包不会被当成可用包。
  - **保留与失败边界**：**只在成功后清理旧包**（失败一个都不删）；单飞（`ErrBusy`），
    长备份不阻塞状态查询。**不做 statfs 预检**——磁盘不足靠「写失败 + 不删旧包」这条错误方向正确的路径兜。
  - 管理面：`GET /admin/backups`（列表 + running 状态）· `POST /admin/backups/run`（后台跑、立刻返回）·
    `GET /admin/backups/:name`（admin 鉴权流式下发，白名单 + 必须出现在列表内，不暴露文件系统路径）。
  - `pb doctor` 增「备份」一项：未启用 = ok + 建议；启用但零份 = warn；`last_error` = warn；
    最近一份 > 48h = warn「定时任务没有在跑」（阈值取 48h 而非 24h，避免一次失败 + 重试造成假红）。
- **与规划稿的偏差（有意）**：
  1. 键名从 `backup.auto_*` 收为 `backup.{enabled,dir,keep,at}`（读起来就是「备份」而非「自动备份的自动」）。
  2. **默认关**且管理台卡片即便未启用也展示——写盘位置由部署形态决定，默认开一个新的大写入源
     会让升级变成风险动作；但运维必须能回答「有没有备份、在哪」。
  3. 未做 `VACUUM INTO` 专项优化：既有导出路径已经是一致快照（4.6.0 起就是这个契约）。
- **落点**：core（`app/backup/{schedule,scheduler}.go` + `bootstrap/auto_backup.go`）·
  server（`pb doctor`）· frontend-core（维护页）· hub（`docs/ENVIRONMENT_VARIABLES.md`）
- **破坏性**：无（默认关闭，新增配置段与端点）
- **验收判据（全部已过）**：
  1. 产出的包能被 `restore` 吃回隔离实例（`TestScheduler_PackageIsRestorable` 端到端断言，
     不是「文件生成了」）。
  2. 连续产出 N+1 个包后最旧被清、数量恰为 N；`keep<=0` 一个都不删。
  3. 失败路径**负对照**：导出失败后旧包一个不删 + 不留 `.partial`。
  4. 同时触发两次 ⇒ 第二次 `ErrBusy`（不会跑出两个包）。
  5. 幂等：同一时刻重复判定只产出 1 个包（今日已有包即跳过）。
  6. 时区：UTC+8 上 03:00 的包日期键必须是**当天**（`ParseFileName` 曾用 `time.Parse` 得 UTC ⇒
     日期键推前一天 ⇒ 每 10 分钟重复导出，已修 + 加`DateKeyOfFileName` 直取字面量）。

#### C. 升级路径统一（文档 + 端侧 hook）—— ✅ 5.4.0 已发货（DSM/QTS），OpenWrt 已随 5.4.1 发货

- **问题**：六端升级方式各异，fnOS 甚至需要 root 或应用中心 UI；没有一份「照做就行」的升级指南。
- **形态**（以文档与端侧脚本为主，不改产品 wire）：
  - `docs/UPGRADE.md`：六端逐步升级步骤 + 升级前三件事（`pb doctor` → 备份 → 记录版本）
    + 回滚步骤 + **兼容矩阵**（支持 N-1 / N-2 直升）。
  - NAS 三端（fnos / qnap / openwrt）的 upgrade hook 对齐：**升级前自动备份**（fnOS 已有
    `upgrade_callback`，另两端补齐同一语义）。
- **验收判据**：文档里**每一条命令都在真机跑过**并附实际输出；不留「大概可以」。
- **已实现形态（以此为准）**：
  - `docs/UPGRADE.md`（hub 仓）= 升级的**唯一真相源**；`docs-site/guide/upgrade.md` 退化为
    `<!--@include: ../../docs/UPGRADE.md-->` 桩（对齐 `deploy-nas.md` 既有模式）⇒ 根治三处漂移。
  - 端侧备份钩子：DSM `spk/scripts/preupgrade`（原先只有 `exit 0`）、QTS `pkg_pre_install`
    **从无到有**；fnOS `cmd/upgrade_callback` 本来就有。三端口径统一：
    `<数据目录>/fileCodeBox.db.bak-<YYYYMMDD-HHMMSS>`、轮转保留 3 份、
    **按文件名排序**（定宽时间戳 ⇒ 字典序即时间序；mtime 会被 `cp -a` / 时钟跳变改掉）。
  - 失败语义按平台可控性区分：DSM / QTS **中止升级**（赌不起的时候不赌 —— 库拷不动通常是
    卷满或权限变了，继续等于**在没有回滚点的状态下跑不可逆迁移**）；fnOS 记日志继续。
  - **OpenWrt（5.4.1 已发货）**：新增 `openwrt/preupgrade_backup`，由 ipk `postinst` 与 apk
    `post-install`+`post-upgrade` 在 `init.d restart` **之前**调用（排在之后拍的已是迁移过的
    库，等于没备份）。这一端**有意不中止安装**：钩子跑在新二进制就位之后，abort 只会把服务留在
    停机状态；且 overlay 常只有几十 MB，flash 写满时 abort 是死结 ⇒ 改为**空间守卫**
    （需求 = 快照大小 2 倍，下限 1 MB，不够就跳过）+ best-effort + stderr/syslog 双写 + 退出码恒 0。
    判据：`scripts/preupgrade-backup-selftest.sh` 9 组用例（轮转只删最旧 / 空间不足不生成且源库
    不动 / 拷贝失败仍退出 0 / 静默截断被字节校验捕获并删残片 / 按 UCI 固化的 `data_dir` 定位 /
    钩子必须在 `restart` 之前调用）+ 5 组变异负对照；打包侧两个 build 脚本显式安装该文件，
    CI 在 ipk 包内清单断言它，并在两条真机升级冒烟（ipk/apk 各装 0.0.0 → 0.0.1）后断言确实
    留下了 `fileCodeBox.db.bak-*`。
  - **只快照业务库**，不含上传文件；跨 4.0.0 的磁盘布局上提仍须整目录备份（文档里明写）。

### 3.2 下一趟 5.2.0 —— 账号与信任

> 主题：admin 是唯一高权账号，站点多半挂在公网或反代后面。

#### A. 管理员 2FA（TOTP）

- **形态**：
  - contracts：`user.thrift` 增三端点（绑定 / 校验 / 关闭），`UserInfoData` 增 `totp_enabled`（optional）。
  - core：RFC 6238（SHA1 / 30s / 6 位）+ **8 个一次性恢复码**（只存 bcrypt 哈希）。
  - 开关：`security.require_admin_totp`（默认 **关**；打开后 admin 未绑定则强制进绑定页）。
  - 前端：安全设置页（二维码 + 手动密钥 + 恢复码**只展示一次**）。
- **破坏性**：无（可选能力；未开启时登录流程一字不改）
- **验收判据**：
  1. 绑定 → 登出 → 登录必须二步；恢复码用一次即失效。
  2. 关闭 2FA 需当前口令 + 当前 TOTP（双因子，防令牌被盗后被关）。
  3. **负对照**：错码 6 次触发既有 lockout 桶（不能绕过失败锁定）。
  4. 存量 JWT 不受影响（只在**登录**时要求，不追溯已签发令牌）。

#### B. 邮箱找回密码

- **前提**：SMTP 已配置。未配置时前端**不显示入口**（capabilities 加 `email_password_reset`）。
- **形态**：`POST /api/v1/user/password/forgot` 恒回 200（防账号枚举）+ 一次性 token
  （30 分钟、落库存哈希、用后即焚）+ 重置端点。
- **验收判据**：
  1. 未注册邮箱同样返回 200 且耗时与已注册无显著差异（防时序枚举）。
  2. token 单次有效、过期失效。
  3. 改密成功后**会话纪元 +1** ⇒ 旧 JWT 立即 401（与 admin 口令重置同口径）。

#### C. 会话管理（登录设备 / 退出所有设备）

- **形态**：epoch 地基已有 ⇒ 暴露成「当前会话列表（设备/时间/IP）」+「退出所有设备」。
- **验收判据**：退出所有设备后，旧 JWT 与旧 refresh 立即失效；**API Key 不受影响**
  （与 admin 口令重置的语义一致：Key 是长期凭据，另行吊销）。

### 3.3 其后 5.3.0 —— 易用与触达

#### A. 目录上传

- **现状**：无 `webkitdirectory` ⇒ 发整个文件夹只能手动多选，且目录结构丢失。
- **形态**：选择目录 ⇒ 相对路径进 `file_code_files` ⇒ 取件页按目录树展示，zip 下载保留结构。
- **验收判据**：
  1. 三级目录 20 个文件：取件页层级正确，zip 解出的结构与原目录**逐路径一致**。
  2. 路径穿越（`../`、绝对路径、Windows 盘符、UNC）一律拒绝（复用 `pathx.SanitizeRelStrict`）。
  3. 空目录、同名文件、超长路径各有明确行为（不能静默丢弃）。

#### B. 多语言（ja / de / ru）

- **现状**：只有 zh-CN / en-US。
- **注意**：`serverDisabledPattern` / `serverNoRootsPattern` **必须保持中文**
  （它们要与后端原始中文报错逐字匹配，翻了就静默失效）——现有 `parity.spec.ts` 已钉住，
  扩语言时把守卫改成「所有语言都必须保持中文」。
- **验收判据**：三种语言 key 集合与 zh-CN 完全一致；切换后全站无中文残留（上述两条除外）。

#### C. demo 站 + 分发跟进（并行推进，不阻塞发车）

- demo 站：独立 compose + 每日重置（重建库与对象目录）+ 只读提示条。
- 分发：iStore PR #810（等上游合并）· 飞牛应用中心（人工通道）· awesome-selfhosted（2027-02 窗口）。
- **验收判据**：demo 站连续 7 天自动重置无残留；外部进程有任何一条实际落地即销账。

## 4. 持续项（每趟车都做，不单独排期）

1. **审计修复批次**：延续 4.8.6 / 4.9.0 的模式——每趟带一批「越权回读 / 归属校验 / 竞态 / 静默失败」。
   这批缺陷的共同特征是**单测全绿、真机才炸**，所以每条都必须有真机或端到端证据。
2. **冒烟跟着功能走**：备份 / 2FA / 目录上传各新增断言，且必须含**负对照**。
3. **新门禁必有自证**：没有负对照的门禁等于没有门禁（4.6.6 的假漂移、4.6.7 的单副本守卫都是先例）。

## 5. 明确不做（写下来是为了以后不再讨论）

| 项 | 结论 | 理由 |
|---|---|---|
| 网盘化（同步盘 / WebDAV 挂载 / 在线编辑） | **不做** | 与「匿名口令快递柜」定位冲突，是另一个产品 |
| 团队 / 组织多租户 | **不做** | 单站点多用户已够；多租户会拖垮权限模型 |
| PWA / 小程序 | **不单独做** | 桌面端一等取件端已发货，能力重叠，成本高一个数量级 |
| 主题系统 / 自定义 CSS | **从 ROADMAP 删除** | 暗色模式已覆盖；回归面大、收益低 |
| 5.0 破坏性收敛 | **不排期** | 当前没有必须删的旧形态；先跑满两个季度 |
| 分享链接 OG 预览卡 | **不做** | 链接指向取件页，预览会泄露「有件待取」这件事本身 |

## 6. 代决项（我按现状拍板，可否决）

| 项 | 代决 | 依据 |
|---|---|---|
| 更新检查默认开关 | **默认开**，可关 | 安全修复到达率 > 一台机器的一次出站请求；请求不含任何实例标识 |
| 定时备份默认开关 | **默认关** | 会占用磁盘；由运维显式开启，但一开启就必须可靠 |
| 主题系统 | **删** | ROADMAP 自 2026-11 起标「建议降级，待拍板」⇒ 本轮直接结案 |
| PWA / 小程序 | **判「不单独做」** | 与桌面端一等取件端重复 |

## 7. 总验收判据（一趟车算不算完成）

每趟车出货前，下列四条必须全部为真：

1. **列车绿**：`release/train.yaml` 的 `state: shipped`，七终端 + 双镜像 + chart 全回挂。
2. **真机绿**：至少一台真实部署面升级到新版本，冒烟 PASS 且 FAIL=0（SKIP 必须写明原因）。
3. **新能力有负对照**：本次新增的每条断言，都能在「把修复回退」时转红（不能是「本来就绿」）。
4. **文档对账**：`ROADMAP.md` / `docs/ENVIRONMENT_VARIABLES.md` / 文档站 CLI 页同步更新
   （漏改文档站 CLI 页曾直接让终验红）。

## 8. 风险与外部依赖

| 风险 | 处置 |
